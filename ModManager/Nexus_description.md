# ER2 Mod Manager v1.7.9

> **v1.7.9:** lazy page build is now on by default (`Ui / lazyBuild`). It was held back because inserting rows at expand time had produced "clicked a mod and nothing opened" three times; the root cause is fixed (the insertion point was being clamped away by its own safety net), every deferred build is self-checked and falls back to a full page build automatically if anything looks wrong, and the expand-window probe has verified the lazy path across four sample points. Opening the MODS page now costs roughly 35-100 ms instead of ~0.3-0.6 s for 970 rows. If you prefer the old behaviour, turn the option off - the full build path is unchanged.

> **v1.7.8:** the hotkey-conflict block got a header with a count and a Hide/Show button. The header always shows ("⚠ Hotkey conflicts: N"), so you can see how many conflicts exist even with the details hidden; the button collapses or expands the detail rows in place (no page rebuild), and the choice is written to `Ui / hotkeyWarnings` and saved immediately, so it survives restarts - the same entry also appears in ER2 Mod Manager's own settings list, so both places stay in sync. Also fixed the reason several conflicts could read as "only one": the detail rows' height was estimated assuming a ~500 px line width, but the label actually has about 400 px available (row 425 minus the label margins), so longer warnings were allocated too few lines, their text overflowed the row bottom and stacked into the next warning - several conflicts visually merged into one blob. The available width is now measured from the content page (with a conservative fallback), so each warning gets the lines it needs, on top of 1.7.7's one-line-per-key aggregation.

> **v1.7.7:** the hotkey-conflict warnings were audited against every config file actually installed, and two defects fell out. First, the conflict scan was more permissive than the renderer: any String entry whose name happens to contain "key" was treated as a hotkey and scanned - the concrete case on this install is More Physics' `ExcludedNameKeywords` (a comma-separated list of prefab names), which joined the comparison, so two mods with the same list default would have produced a fake "hotkey conflict". String entries now also have to look like a key (a single word such as F5 / Space / Mouse0, an A+B combo, or empty), so name lists, paths and sentences are out. Second, three bindings on the same key used to produce two lines ("A and B", "A and C") that never mention B vs C; conflicts are now aggregated to one line per key listing every binding, which also surfaces self-conflicts inside a single mod. With debug logging on the scan reports how many groups it found. For reference, this install currently has three real conflicts, all listed on the page: F (Advanced Combat Movement "Follow Or Marker" × ER2 Battlefield Commander "Key Scatter"), F9 (ACM "Restart Mission" × Battlefield Commander god key) and G (Battlefield Commander "Key Pack" × ER2 Universal Generation panel key).

> **v1.7.6:** the fade now covers page turns, setting groups and individual entries too, not just expanding a mod. A whole page (entering the MODS page, coming back to it, or a rebuild) fades in through a single canvas group on the page container; a setting group and an entry's description line fade exactly like a mod's settings, all timed by `Ui / revealMs`. Page-turn flash is also hardened: the per-frame cleanup that removes native rows the game's asynchronous page filler drops into our page used to `Destroy` them, and destruction only takes effect at the end of the frame - so those rows were still drawn for one frame, which is precisely what a page-turn flash looks like; they are now deactivated first (immediate) and destroyed after. The page path additionally re-checks row hit areas for the opaque-white state a disabled row can come back with (the same white block fixed in 1.5.13, which recurs on any "deactivate then reactivate" path - and building a page is exactly that, for a hundred rows at once), correcting and warning when found. The page fade cannot replay in a loop: repeated rebuilds fade the page once rather than per rebuild (a rebuild burst would otherwise read as the page repeatedly fading out, which is worse than a flash), and page builds above 300 rows get a single hidden frame instead so the animation can never become the expensive option. With debug logging on, every page build is now probed like expansions are (same frame, +0.03 s, +0.13 s, +0.36 s) reporting how many distinct row positions the page has settled on, the worst hit-area alpha, the content height, the count of foreign non-mod-manager objects in the page, and the frame number; the tab and page-build log lines carry the frame number too, so a build landing a frame after the key press is visible rather than inferred. (1.7.5's log already verified the expand path: no unsettled rows, no opaque hit areas, constant content height across all four samples - which is what made the remaining page-turn flash stand out.)

> **v1.7.5:** expanding a mod no longer flashes. With the lazy page build, expanding a folded mod builds its setting block on the spot; the rows are laid out within that frame, but a few appearance details settle a beat later, so one or two frames could be drawn half-formed - the "every option blinks once" you see. Newly built rows now fade in (`Ui / revealMs`, 200 ms by default) instead of appearing instantly: the space opens at once and the content follows it, which turns the expand into a transition rather than a blink, and since a canvas group does not participate in layout the rows still take their place and the rows below do not jump an extra time. Row hit areas are re-checked on every expand as well - a disabled row loses its renderer colour and gets it re-applied on re-enable by the selectable's state transition, and when that chain misses a beat the hit area comes back opaque white (the same white block fixed in 1.5.13); those rows are now corrected on the spot and reported in the log as a fault, so it stays visible with debug logging off. The fade can be switched off with `Ui / revealAnim`, and it is skipped for expansions of more than 300 rows so a very large mod still appears instantly instead of risking a stutter. With debug logging on, each expand also logs an `[MM-flash]` probe at four points in time (same frame, +0.03 s, +0.13 s, +0.36 s) reporting how many distinct row positions the layout has settled on, the worst row hit-area alpha, and the content height - the three physical causes of a flash, so any further report can name the cause instead of guessing at it.

> **v1.7.4:** fixed the lazy build inserting a mod's settings at the bottom of the list instead of under its title (the "clicked and nothing opened" report). The insertion point was computed correctly but then hit a safety clamp reading "if the target is before the newly created rows, use their position instead" - and since the new rows are always appended at the end, the title is always before them, so the clamp fired every time. It is gone; the position is trusted now, and the remaining structural self-check is what caught this in testing (it reported "row[0] not contiguous" and fell back to a normal page - hence why clicking again later worked). The defect could only occur on the lazy path, which is why the option has always been fine when off.

> **v1.7.3:** the settings page can now open far more cheaply with `Ui / lazyBuild`, and that option is fail-safe. Building the page creates every mod's every setting up front (970 rows, 0.34-0.59 s measured) - the pause you feel when entering the settings; with the option on, a folded mod keeps only its title row and builds its settings on first expand. Earlier attempts at this were withdrawn three times over "clicking a mod shows nothing"; those causes are now understood, and the page now verifies its own deferred builds (rows directly under the title, page height keeping up) - on failure it retries and, after two failures, abandons the lazy path for the session and rebuilds normally, logging the reason. Worst case is one ordinary page build. Off by default until confirmed in-game. The build log also reports a phase breakdown.

> **v1.7.2:** a favourited mod now expands on the first click - the favourites entry only marked the mod as open without opening it, so the next title click merely undid that invisible state (hence "needs two clicks"); both paths now share one function. Hovering a favourite entry now brightens its text (the old feedback was a 3.5% white row tint, invisible on a dark background), the star / Restore / Reset all / Copy all buttons got their hover-and-press feedback back (it had been switched off since 1.3.1), and a favourited mod's star is now gold instead of the same dim grey as the rest.

> **v1.7.1:** fixed the favourites block being invisible - it took up space at the top of the page while showing nothing. The label rectangles were pinned to the middle vertically with zero offsets at both ends, which leaves them zero pixels tall, and a text field with no height draws nothing; the rows were active and laid out all along, so the page was just pushed down by a blank strip. Those labels now use the same fixed-height sizing as the mod info line (the same defect on the \"default value\" label is fixed too). Also: mods always start folded - which mods were open is no longer saved across restarts (which setting groups you opened inside a mod still is).

> **v1.7.0:** added **favourite mods** - each mod's title row has a star on its right; click it and the mod appears in a Favourite mods block at the top, where clicking it expands the mod and scrolls straight to it (saved across restarts, up to 24). Also **removed the search box** from 1.6.x: filtering this list by keyword disturbed the page far more than it helped, since one keystroke could restructure hundreds of rows. Favourites cover the same need without moving anything.

> **v1.5.25:**> **v1.5.25:** setting groups default to **collapsed** again, as they always did. 1.5.23 had flipped them to expanded while hunting "clicking a mod shows nothing", but the real cause was the expanded-state memory having been switched off in 1.5.20 - and that memory is back on, so the groups you open are remembered across sessions. With the memory working, the original default no longer leaves a mod looking empty.

> **v1.5.24:** the experimental "lazy page build" is now **off by default and marked as not recommended**. It cut the cost of opening the MODS page from 942 rows / ~300 ms to 46 rows / ~60 ms, but inserting rows at expand time has produced "clicking a mod shows nothing" three times (1.5.9, 1.5.19, 1.5.23). This build fixes one concrete defect - the insert anchor was recorded as "the container's last child", and once stale the new rows were appended to the end of the list instead of under the title, so the content existed but sat far below the visible area. It now uses the title's own parent transform. The switch still stays off until confirmed in-game; opening the page costs ~0.3 s again and expanding is back to plain show/hide.

> **v1.5.23:** setting groups inside a mod now start **expanded**, and the expanded-state memory is back on by default. Two halves of one problem: a mod with several groups used to open showing only its group headings (4-7 dim lines, every real setting folded one level deeper), so it looked empty; and 1.5.20 turned off the memory that kept that state, reasoning it only mattered across restarts - which was wrong, since it was also the only place the state was ever kept. Expanding a mod now shows its settings directly; groups remain collapsible if you prefer the compact view, and ones you collapse on purpose stay collapsed.

> **v1.5.21:** two fixes. The intermittent flash was the row inset: the vanilla viewport alternates between reserving scrollbar space and not (target flips 24 <-> 8), and every flip wrote a new size and force-rebuilt the whole column in the same frame. The row width barely changes (426 <-> 425), so the forced rebuild is now kept only for the first apply and later flips just mark the layout dirty. And "expanding a mod shows nothing" under the lazy page build: the rebuild only covered the row container, which is itself a child of the content page - new rows landed outside the visible area even though they existed, were active and the content had grown. The relayout now rebuilds both layers, refreshes the canvas, and repeats once on the next frame.

> **v1.5.20:** the expanded-state memory is now **off by default**. Within a session it was never lost anyway (the state lives in memory, surviving page turns and reopening the settings), so persisting it only mattered across restarts - a small win - and it worked against the lazy page build, since a mod remembered as expanded must have its settings built as soon as the page opens. The feature and its option (`Ui / rememberExpanded`) stay, just no longer by default.

> **v1.5.19:** added an optional lazy page build (`Ui / lazyBuild`, **off by default**). Opening the MODS page builds every setting up front - 942 rows for 28 mods, measured at 0.3-0.4 s - which is the brief pause when entering the settings; with the switch on, a folded mod keeps only its title row and builds its settings on first expansion. It stays off by default because an earlier attempt (1.5.9) produced "clicking a mod does nothing" without ever being explained; with the switch on the mod now logs everything needed to pin that down.

> **v1.5.18:** fixed the mod info line looking wrong. It was drawn with the helper meant for entry descriptions, which reserves height from the character count - so the line came out twice as tall as it should and pushed the list down. It is now a single fixed-height line, smaller font, truncated by measured width, and it no longer repeats the mod name the title already shows.

> **v1.5.17:** four quality-of-life fixes. **Labels stop mangling acronyms** — AI showed as "Ai", HUD as "Hud", UI as "Ui", MG42 as "Mg 42"; a whitelist of known abbreviations now keeps them uppercase and joins an abbreviation to a following number (MG42, M1), while SCREAMING_SNAKE_CASE keys still render as "Max Count" rather than "MAX COUNT". **Third-party ConfigurationManager attributes are honoured** — entries marked `Browsable = false` (a mod's internal or debug knobs) stay out of the list and a declared `Order` is respected, both read by reflection so nothing has to be installed. **Every mod now shows its identity** — full name, plugin GUID, version and setting count on one dim line, and "Copy all" includes it, so a screenshot or pasted config identifies the exact mod and version. **Expanded state survives a restart** — the mods and sections you had open are restored next launch (`Ui / rememberExpanded` turns it off).

> **v1.5.16:** the page-turn click sound is back — and the cause was timing, not a failure. Playing the click after the page work (1.5.15) still left the MODS page silent, while the vanilla pages clicked normally in between; the click probe never reported a single failure, so the call succeeded and the sound was simply swallowed. The page rebuild recreates a thousand-odd UI objects in one frame, and a click played into that frame never comes out. Page-turn clicks are now **scheduled instead of played** — queued and picked up 0.25 s later, once the rebuild has settled.

> **v1.5.15:** second attempt at the silent page turn: the click used to be played before the page work started, so the rebuild that followed destroyed whatever had just begun playing. Playback is now ordered after the page work — after the MODS page is rebuilt when entering, and after the page switch when leaving it or looping back.

> **v1.5.14:** diagnostics only. The page-turn click had gone silent while every branch still called the click sound, so the only place a failure could hide was the empty catch around that call. It now logs any failure, which ruled out an exception and pointed the next two builds at playback timing.

> **v1.5.13:** the flash is found, on camera. Frame-by-frame brightness analysis of a screen recording shows the exact signature: average screen brightness 125 -> 344 -> 97, two frames (~67 ms) at the moment the MODS page appears, with every row covered by a full-width white block. That block is the invisible click area each row carries - a white image whose transparency is configured through a Button colour block. The catch: setting a colour block only stores the configuration; at the moment the Button is added its OnEnable paints the renderer with the DEFAULT block (opaque white), and our transparent normal only applies on the first state change - so the click areas show as solid white for the first two frames, wherever rows are created or re-shown. The normal colour is now painted onto the renderer immediately, and the click areas are transparent from frame one.

> **v1.5.12:** reverts the deferred building from 1.5.9. The game log proved the expand handler ran and the rows existed, yet the content stayed invisible - and that started exactly with 1.5.9, so the risky optimisation goes and page building is back to creating everything up front. The scroll-position restore from 1.5.11 is removed for the same reason: it was an unverified guess. In their place, one decisive diagnostic: after every expand the log now reports how many rows are active, how many of those fall inside the viewport, where they sit on screen, and the scroll position - whichever of the three is still wrong, the next log pinpoints it directly.

> **v1.5.11:** the flash has a mechanism now. Expanding or collapsing anything changes the height of the scrollable content, but the scroll position is stored as a fraction of that height - so the moment the height changes, the same fraction points at a different place and the entire list slides for one frame. That is the flash, and it explains why it looks identical to the old "flash after clicking a setting". The list now remembers where you were looking in pixels and restores it after the height change. Also added one log line per expand/collapse, which is the only way to tell whether "clicking does nothing" means the click never arrived or the handler had nothing to show.

> **v1.5.10:** fixes a regression from the previous build where clicking one mod could expand a different one - the deferred building remembered row positions from when the page was built, and expanding a mod above shifted all of them, so rows landed under the wrong mod. Positions are now resolved at the moment of insertion. Second attack on the flickering options: the row width was compared against the container's current size, which the parent layout recalculates every frame, so it rewrote the width and relaid out the entire column on every single frame. It now compares against the last intended value, so nothing is rewritten unless the target actually changes. Diagnostics now report how many writes happened per window instead of one throttled line, since the frequency was the whole point.

> **v1.5.9:** two fixes that came out of the game log rather than guesswork. The flickering options: every click was pushing a height onto the row container instead of the settings page's content object, and since that container carries a content size fitter, the height was recalculated away on the next frame and bounced between two values (measured at 1644 <-> 1784 px), relaying out the whole column each time. Heights now always go to the real content object, so they settle. The unresponsive paging: opening the page rebuilt every setting of every mod, including those inside folded-away mods - around a thousand objects per page turn. Folded mods now keep only their title row and build their settings the first time they are expanded; nothing rebuilds the whole page. Build cost is logged so this is measurable.

> **v1.5.8:** found the click flash, and it was not in the mod list at all. Leaving the MODS page with the left arrow was being handed back to the game's own tab handler. Since MODS is appended after the last vanilla page, the page index it carries (4) is out of range for the game, which only knows pages 0..3 - so the game refilled the entire settings panel from an index it does not understand. That full repaint is the flash, and it happened on every exit from the page ("tab left:pass-native cur=4 myIndex=4" in the log). The left arrow is now handled by the MODS page itself and returns to the last vanilla page, mirroring how the right arrow opens it. Also closed a gap in the previous diagnostics: the rebuild that runs when the settings menu is reopened was not being logged, so "no rebuilds occurred" had only covered one of the two rebuild paths.

> **v1.5.7:** no behaviour change, diagnostics only. Still hunting the click flash: the previous theory (that the page was being rebuilt) was checked against the game log and turned up nothing at all - no rebuild occurred during testing - so the flash comes from somewhere else. This build adds a probe that detects rows sitting on top of each other right after a forced relayout, which is what a white flash physically is: for one frame the rows share a position and their light value boxes stack into a white block. It also throttles the row-inset diagnostic, which previously printed every single frame. Both only run when the Debug switch is on.

> **v1.5.6:** hunting the remaining click flash. The page self-repair that runs every frame treated a short list as a broken one: it only looked at the container height, and since the content height has a floor of 200 px, a list that is genuinely short (few mods installed, or most of them folded away) always matched the "layout never ran" test and forced a full page rebuild - which is exactly what makes the whole page flash. It now compares the requested height against the rendered height, so a short list is left alone and only a truly unlaid-out page is rebuilt. Rebuilds are also logged with their reason (`ModManager: rebuilding MODS page ... reason=`) so any remaining flash can be identified instead of guessed at, and the page outlines are finalised right after building so the first frame no longer trips that check.

An in-game settings manager for Easy Red 2 BepInEx mods: adds a native-looking MODS page to the game's settings menu where every plugin's config can be tweaked live — with **zero hardcoded translation tables**, so it automatically works with any mod you install, now and in the future.

## Description

- Adds a **MODS** page inside the game's native settings (Esc menu) — every loaded BepInEx plugin's options appear as vanilla-style controls: toggles, dropdowns, sliders and numeric inputs.
- **Fully automatic, zero maintenance**: the manager auto-discovers every loaded plugin and auto-renders whatever config entries each one exposes. Config labels are humanized from their key names (`enableAIVaulting` → `Enable AI Vaulting`), so third-party and future mods show readable names without any per-mod lookup table.
- **Alphabetical mod list** with letter section headers; "Easy Red 2"/"ER2" prefixes are stripped for sorting and grouping (the full name is still shown when a mod is expanded).
- Mods with no config entries still appear as read-only "installed" entries, so you can see everything that's loaded.
- Controls are cloned from the game's own settings UI, so it looks and feels like stock.
- **Staged auto-save**: changes are saved automatically when you leave the settings.
- Handles bool / int / float / string / KeyCode entries — free-form strings get a text input, hotkeys are re-bound by clicking the button and pressing the new key, and every setting is guaranteed to render.

## Installation instructions

1. Install BepInEx 6 (IL2CPP) for Easy Red 2.
2. Copy `ER2_ModManager.dll` to `<Easy Red 2 folder>/BepInEx/plugins/`.
3. Launch the game, open Settings (Esc) → the MODS page lists every plugin's configuration.

## Main features

- Native-styled MODS page cloned from the vanilla settings UI.
- Auto-discovers every loaded BepInEx plugin and renders all its config entries — no hardcoded mod list.
- Alphabetical list with letter headers; ER2/Easy Red 2 prefixes stripped for quick lookup.
- Humanized config labels (camelCase/snake_case → readable text) for any mod, including third-party ones.
- Toggle / dropdown / slider / numeric-input / free-text controls for all common config types.
- Numeric inputs with range hints (with engine-font fallback so digits always render).
- Hotkey capture rebinding (including enum-typed hotkeys).
- Changed values are marked so you can see what differs from the defaults, and any single setting can be restored on its own (its default value is shown next to it).
- Whole-mod "Reset all" is two-step: the first click only asks for confirmation and expires on its own.
- Settings the author marked as restart-only are labelled, and saving such a change tells you how many need a restart.
- Per-mod copy & reset in the footer, with on-screen flash feedback.
- Two-way page looping (first page ⇄ MODS page) with native click sounds.
- Staged auto-save; honors each plugin's master switch.
- Compatible with the game 2.1.x settings rework.
- Honours third-party ConfigurationManager attributes: entries marked hidden (`Browsable = false`)
  are not listed, and a declared `Order` is respected (read by reflection, no dependency).
- Each mod displays its own identity (full name, plugin GUID, version, setting count); "Copy all"
  includes the same line, so a screenshot or a pasted config pinpoints the exact version.
- Remembers which setting groups you opened inside each mod, across game restarts (`Ui / rememberExpanded`, on by default). Mods themselves always start folded.
