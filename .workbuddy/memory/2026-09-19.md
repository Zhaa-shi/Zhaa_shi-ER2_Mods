## 起点（承接 zcode 会话 sess_5d645395…，该会话 11:18 因 quota 用尽中断）
- 会话在做 SquadCommand「右键友军 → 派兵走过去 → 到达后自动开双方背包」的 bug 排查；11:18 已编译部署 1.4.9 但**未实测**。
- 1.4.8 实测证据（`BepInEx/LogOutput.log` 11:10）：
  - `会合请求 Backpack · Floyd Upham 距离=12.3m → 派 Nolan Currey 前往`（派兵分支跑到了）
  - 之后**没有任何**到达/超时/停驻日志 → 到达检测整段没执行
  - 用户再次右键时 `距离=0.9m → 即时开窗` → **派出去的兵其实已经走到贴身**（用户："近到都把那个单位挤开了"）
  - 结论：不是距离阈值问题，而是「任务被静默清掉 或 LootTick 没跑」。1.4.8 既无 trace 也无 ResetLoot 原因日志，无法区分。

## 本轮改动（SquadCommand v1.4.9，沿用原版本号）
1. **双路驱动 LootTick**（会话已做）：`GodViewController.Tick` 的调用点位于 `if (!Active || flyingToSquad) return;` 门控之后（历史遗留静默失效风险）；`BackpackPanel.Draw()`（OnGUI 主循环，图标一直在画 = 全程验证存活）也调一次。0.25s 节流、双调幂等。
2. **ResetLoot 全程记原因 + 2s 跟踪日志**（会话已做）：`会合任务重置（原因）` / `会合进行中 dist=X.Xm 重派=N/8`。
3. **任务与窗口解耦（本轮新修，关键）**：`BackpackPanel.CloseAll()` 原来顺手 `ResetLoot("CloseAll 清场")`，而**取消/更换选择链 `ClearSelection()` → `CloseAll()`** 也走这里 → 会合途中任何一次选择变动都会静默清掉在途任务（walker 照走，没人判定到达）。现在 `CloseAll` 只关窗口/拖拽；新增 `BackpackPanel.CancelLoot(reason)` 才杀任务，只在三处调用：进 RTS（GodViewController ~1826）、接管单位（~2092）、退出 RTS（~1856）。
4. **停驻即开窗**（用户定案「在停止后再触发一次开背包」）：独立于 packRange 的第二通道。0.25s 采样位移 <0.2m 连续 0.8s（任务开始后 1.5s 宽限，避免刚接令未起步就判停）→ 判「停了」；停在 `max(packRange, 5m)` 内直接开窗（LogAlways 记实际距离），停得远了才继续重派/等超时。
5. 到达开窗抽成唯一收口 `ArriveOpen(walker, why)`（先取任务态局部量再 ResetLoot，避免收口过程被重入清空）。

# 2026-09-19（第四轮）— SquadCommand 1.4.12：穿戴「只能脱不能穿」诊断+双通道修复

# 2026-09-19（第六轮）— SquadCommand 1.4.14：性能优化 + 发布

## 优化项（**不动行为**，只消除重复 interop 调用与临时分配）

1. **`GetAllFriendlySquads` 加 0.3s 缓存**（`SquadCmdLogic.cs`）
   - 原实现每次调 `CollectSquads()` → 遍历**全场景所有 Creature** + 逐个 `TryCast<Soldier>` + 分配 Dictionary/List；
     而它在「进 RTS / 接管 / 编组 / 死亡重挂」流程里会被**连续多次**调用 = 数百毫秒卡顿感主因。
   - 返回共享 `friendlyCache`（约定调用方只读）；新增 `GetAllFriendlySquadsCopy()` 给需要长期持有的场景。
   - **已逐个核对 5 个调用点，全部只做 foreach 遍历、不修改**（安全）。

→ 结论：**看门狗误杀 + 6 次触顶后永久放弃**，物品页签永远建不起来。

## 误杀机理（本轮核心认知）
- 加载战斗场景期间**主线程被 Unity 占住** → 探测协程拿不到 tick、**心跳无法刷新**；
- 而 `Time.unscaledTime` 是**墙上时钟、照常前进** → 心跳"停跳"是**假象**，不是协程死了；
- 看门狗据此重启，`probeRestarts++`，**6 次触顶 → `probeState=3` 永久放弃**。
- **本质**：2.0.3 的 150s 硬阈值、2.0.4 的 20s 心跳判活 —— **同一个错误：用"时间流逝"当"协程死亡"的判据**。

## 修法（`ItemCatalog.cs`）
1. **彻底移除"自动放弃"**：`probeState` 由 0/1/2/3 四态 → **0/1/2 三态（无放弃路径）**。
   `ProbeWatchdog()` 改「**不判死、只续跑**」：
   `if (Ready||Failed) return; if (probeState==1) return; if (probeState==0) Begin();`

```

```

**为什么这次对**：判据是"**协程自己跑的帧数**"，与时间无关。同时满足两个矛盾需求——
① 场景加载期间**看门狗自己也没被调用** → 不会去比对 → **不误杀合法停摆**；
② 看门狗被调用时协程**必须也在涨** → **真死必被发现**。
`Time.timeScale` / 场景加载 / 墙上时钟**全都骗不过它**。

**通用律：判活要让"被检测者"自己产出与时间无关的存活信号（帧计数/递增序号），

## 教训（可复用）
**IMGUI 里"某控件一画，后面整块空白"→ 先怀疑该控件的原生方法被裁剪，而不是布局/数据。**
排查顺序：看异常发生在"哪一段绘制之后"，**幸存/消失的分界线就是出事控件的位置**。
另：IL2CPP 游戏的面板**能用按钮就别用输入框**；字母/筛选按钮行别按数量均分宽度，固定宽 + 自动换行。
