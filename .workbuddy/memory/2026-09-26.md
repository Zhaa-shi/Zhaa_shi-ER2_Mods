## UniGen 2.5.42 —— 验证轮死代码定案（07:00-07:10）

玩家："列表在进战斗后一直没有变化"。日志：读盘命中（560 条）后 ItemCatalog **零活动**——没有"开始验证"也没有"验证完成"。

### 根因：early-return 吞掉了就绪态分支
`ProbeWatchdog()` 第一行 `if (Ready) return;`，而验证/补漏触发块写在它**后面**（`if (Ready && probeState == 2)`）。读盘命中使 Ready **启动瞬间**就为 true → 函数每秒都在第一行返回，触发块是**死代码**，从未执行过。GenRunner.cs:838 的调用方正常（每秒、任何场景），ModCatalog 正常工作反证了这点。

### 修法
触发块整体挪到 `if (Ready) return;` 之前；条件从 `cacheHit(=cacheWritten&&lateDone)` 简化为直接分支 `cacheWritten`（读盘命中 → 验证轮；运行时枚举 → items 补漏轮）。另确认：**版本号 sed 连续两轮 no-op**（2.5.39→41 的 sed 源串与文件实际值不符，文件一直停在 2.5.40）——本轮从 grep 到的真实值 2.5.40 起步改 2.5.42。

### 教训（高价值）
1. **给 early-return 的函数加新分支时，先画控制流**：服务于"已就绪"状态的逻辑必须放在 `if (Ready) return;` **之前**——就绪态恰恰是这个 return 最先吞掉的状态。静态读代码时对"不可达块"要有警觉（编译器对不可达语句几乎不警告）。
2. **sed 批量改版本号必须先 grep 实际值再替换**，替换后立即 grep 验证——连续两轮 no-op 导致"部署的版本号"与"实际代码"错位，排查时先浪费了一步。

### 状态

**待复测**：进战斗后 10 秒应出现"开始验证物品目录磁盘缓存（当前 560 条…）"→"磁盘缓存验证完成: 缓存=560 实枚举=15xx"→ 列表自动补全；下次启动读盘即完整。

### 根因：守卫值在一条路径上永远为 0
触发条件含 `readyAt > 0f`；读盘路径的 `readyAt = Time.unscaledTime` 取自**插件 Awake 那一刻**——那时游戏一帧都没跑过，`Time.unscaledTime` = 0 → 守卫恒 false，两条后台轮**永久**不触发。

修法：Ready 分支开头**自愈**（`readyAt <= 0` 即用当前时间补建基线并记日志）。

### 通用教训（与上一轮同族，本轮第二次犯）
**"守卫值"必须与"谁在什么时机写入"一起审查**：一个 `x > 0f` 形式的判据，如果存在一条路径在"时钟尚未开始"的时刻写入 x，该路径就被静默拒绝。凡是"计时基线 + 阈值"组合，都要么保证基线在所有路径非零，要么在消费端自愈。

## UniGen 2.5.45 —— 条数偏少的真因：单轮快照 vs 逐步长成的数据库（07:45-08:05）

玩家确认："多出来的"是**物品页分类页签**（修复正常产物）；但**列表内容量仍然明显偏少**。

### 决定性测量：直接数缓存文件
```
weapons 549  gear 407  ammo 204  food 4   ← 官方合计 1164（+ mod 608 = 头里的 1772）
历史"完整"枚举：weapons 701  gear 542  ammo 208  + items 58 = 1509
```
**缺口 287 条官方物品**（武器 -152、装备 -135、items 类几乎没进来）。

### 真因
官方物品库**随游戏进程逐步长出来**（不是一次性加载完）：本轮验证轮在开局 ~23s 就跑了 → 只拿到 1164；历史上 1451 那次是在长时间游玩后枚举的。`WaitForAssetBundleLoaded("er2bundle")` 只保证"资源包已加载"，**不保证 ItemsDatabase 的条目都已登记**——两件事不是一回事。玩家的直觉（"进战斗后 mod/物品才加载，进得不够快列表就少"）是对的方向，只是官方条目同样如此。

### 修法（2.5.45）：多轮累积验证
- 单会话最多 3 轮，间隔 10s → +30s → +120s；每轮只增不减地并入（`Add` 按 Id 去重）。
- 某轮**不再新增** → 判定稳定 → 此时才 `WriteCacheToDisk(true)` 标 verified=1。
- 仍在增长时写盘但**标 verified=0**（下次启动继续补）——"未稳定不得声称可信"。
- 保留签名跳过：一旦稳定 → 后续启动零原子调用（省下每轮 ~20-55 秒冻结）。

### 本轮踩到并纠正的自身错误
先把现有缓存头手工标成 `verified=1`（想省玩家一次冻结），随后才意识到**那会让多轮补全永不启动**——立刻改回 `verified=0`。教训：**"跳过工作"的标记与"还需要工作"的目标互斥，加标记前先确认当前状态是否真的已经达标**。

### 可复用经验
**"昂贵的一次性采样"不能当作全量**：数据源若是逐步长成（流式/按需注册），必须用"累积 + 稳定判定"，并且**只有稳定态才允许写入"可跳过重算"的标记**。单一时刻的快照既不能证明完整，也不能证明稳定。

### 先说结论：lazyBuild 性能目标达成，但引出功能回归
日志实测 `page built in 29~69ms - rows=46 mods=28`（旧路径 942 行 / 276~432ms）—— **进页建页成本降到约 1/5**。但展开出问题。

### ① 偶发闪：行内缩状态翻转时同帧强制重排整列
证据：`row inset writes=3~4 in last 5s (target right=24.0, content 450) / (target right=8.0, content 433)`。
原生 Viewport 在"预留滚动条 17px / 不预留"两态间切换 → 目标值 24↔8 跳 → 旧代码每次 `changed` 都写 sizeDelta + `ForceRebuildLayoutImmediate(crt)` → **整列同帧重排 = 闪**，只在翻转那一下出现 = **概率非 100%**。
**关键观察：行宽几乎不变（426 ↔ 425）** → 补偿逻辑本身正确，错的是"顺手强制重排"。
修法：强制重排只保留给 `float.IsNaN(lastInsetW)` 的**首次应用**，之后 `MarkLayoutForRebuild`（Unity 正常布局阶段自会处理）。

### ② 延迟建页"点开没内容"：重建只覆盖一层
v1.5.19 布的诊断这次给了完整数据：
```
[MM-lazy] 状态 'ER2 AI Food': containerActive=True containerH=1636 preferred=1636 rows=11 inactiveInHierarchy=0 firstInactiveParent=ok [0]y=0,h=18,act=1 ...
ModManager: state mod 'ER2 AI Food' rows=11 active=5 onScreen=5 rowY=-1722..-381 viewportY=0..0 vnp=1.00 contentH=1806
```
行全建了、全激活、父链干净、内容高度也涨了（1644→1806）、零异常——但 **rowY 世界坐标整体为负**（正常路径对照：`rowY=129..1060` 正值）。
根因：`RelayoutContainer` 只 `ForceRebuildLayoutImmediate(container)`；container 带 ContentSizeFitter（高度自设）**同时又是 contentPage 的子物体、位置/高度受宿主那层支配** → 宿主没重算，新行落在可见范围外。

### 根因（一个恒命中的"兜底"）
```csharp
insertAt = body.titleRow.transform.GetSiblingIndex() + 1;   // = 28（正确）
if (insertAt < before) insertAt = before;                   // before=71 ⇒ 28<71 恒真 ⇒ 取 71 = 容器末尾
```

新建行**总是先追加在末尾**，标题下标天然小于 `before` → 兜底**必然命中**，把正确插入点换成末尾。
**它从来不是兜底，它就是行为本身。**
**为什么常规路径一直正常**：建页时行紧接着标题建，`titleIdx+1 == before` → 兜底是**空操作** ⇒ 缺陷只在延迟路径出现，
所以四轮（1.5.9/1.5.19/1.5.21/1.5.23）都没暴露。
**修法**：删掉该兜底，位置直接采信；只留硬性防御（下标非法 → 退化为追加）；安全网交给自检。

### 教训（写入台账 + 技能）
1. **"保护性钳制"的条件必须实测命中率**：若它在正常路径上恒命中，它就不是兜底而是行为本身。**写兜底时把
   "是否命中"打进日志**（本次靠 `insertAt=71 before=71` 一眼看穿）。
2. **自检 + 有界回退的价值被实证**：过去四轮同现象都靠"玩家报症状→猜→改→再测"；这次一条
   `row[0] 位置不连续(idx=71 ≠ 28)` 直接给出物理成因，且玩家侧最坏只是"一次常规建页"。

1. **扫描端比渲染端宽松**：String 条目键名含 key/toggle 即被当热键扫描，而渲染端还有

   两个 mod 名单默认值相同就会报假冲突。**修**：扫描端加 `LooksLikeKeyValue(value)` 形状校验
   （单词/A+B 组合/空值算热键；含 `,;\/:=` 或 >24 字符排除）。只动扫描端，渲染端不碰。
2. **一对多配对不全**：A/B/C 同用一键旧实现报"A 与 B""A 与 C"两行（map 不更新），B-C 关系看不到。
   **修**：按键值聚合，一键一行列出全部绑定（同 mod 自冲突也列出）。
3. 顺带：debugLog 下输出 `hotkey conflict scan: N group(s)`。

### 审计确认没问题的
渲染端 String 改键按钮有 `LooksLikeKeyList` 守卫（ExcludedNameKeywords 显示为下拉 ✓，不是功能误伤）；
`KeyCode=None` 跳过 ✓；`AddWarningRow` 行高估算无实锤问题未动；全工作区无 `KeyboardShortcut` 使用

### UniGen 2.5.48 —— 启动报错刷屏真因（映射名负缓存缺失）（12:20-12:50）
玩家："启动游戏一直报错，很多很多"（`Prop ID '...' not found! - MappedResources contains: False`）。
**定位**：UniGen 枚举目录时对每个物品调游戏 `GetMappedResourcesName()`（显示名策略 2.4.0 起），

缓存命中的会话零枚举 → 干净；缓存无效/未验证的会话 → 刷屏（"有的会话报有的不报"的原因）。
纯日志噪声（显示名本来回退 io.name），但几百条 [Error] 不能留给玩家。
**修**：映射名负缓存——`MappedNameFailed`（会话 HashSet）+ 磁盘缓存 `#u\t<id>` 行持久化（读回恢复），
查不到的 id 不再问游戏；`ResetForFullRescan` 清空。显示结果一字不差。
